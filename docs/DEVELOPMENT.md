# 每天一款游戏的协作和交付

只有 `main` 是长期分支。每天一个新游戏、一个独立工作目录、一个 PR；人工的内容和设计调整也通过短期分支进入主分支。本次不配置定时器，未来的 GPT 定时任务调用同一流程即可。

## 代码格式与静态检查

所有工作区共用根目录的 Prettier 和 ESLint 配置，工具依赖固定版本并通过 `npm ci` 安装。JavaScript 使用双空格缩进、单引号、分号、100 字符换行宽度和 LF 换行。

```powershell
npm run format       # 统一源码、配置和文档格式
npm run format:check # 只检查格式
npm run lint         # 检查 JavaScript，要求零警告
npm run lint:fix     # 自动修复可安全处理的问题，剩余问题需手动处理
```

ESLint 按浏览器、Node 和 Worker 运行环境检查代码；有意保留的未使用参数以 `_` 开头。生成的关卡数据、解题夹具、锁文件、依赖、本地私密配置和构建输出不参加格式化，避免破坏已发布关卡哈希或生成结果的复现。

`npm run check` 同时执行 ESLint、Prettier、原有语法和包边界检查，以及构建后的 PWA 清单检查。先运行 `npm test`（包含构建），再运行 `npm run check`。PR 验收和发布工作流已使用同一检查入口，格式或静态检查失败会阻止后续步骤。

纯文档变更仅包括根目录 `README.md`、`AGENTS.md`、`docs/` 下的 Markdown 和 `games/<id>/README.md`。这类 PR 保留轻量的 `game-verification` 必需检查，但跳过依赖安装、游戏测试、构建与浏览器验收，避免整条工作流跳过后阻塞合并。混入任何代码、配置、工作流或网站资源时仍完整验收；重命名同时检查源路径与目标路径。纯文档推送不触发部署，机器人合并纯文档 PR 后也不显式发布；手动发布与恢复操作仍可使用。

## 开始和重试

在仓库中运行：

```powershell
npm run game:task -- start honey-trail
npm run game:task -- start honey-trail 2026-10-29 C:\Users\dong\dev\game\game05\worktrees\honey-trail
```

日期默认按 Asia/Shanghai 计算。工具读取本地分支、远端分支以及包括已关闭 PR 在内的历史记录；同一天已有任务就返回原任务，不能更换游戏 ID 再创建第二款。已关闭任务需要人工决定重新打开或继续原修复流程。未通过检查的游戏延期，次日任务独立开展。

分支格式为 `game/YYYY-MM-DD/<id>`、`design/<id>/<主题>`、`fix/<id>/<问题>` 和 `platform/<主题>`。游戏 ID 使用小写字母、数字和连接线，以字母开头。独立目录中先运行 `npm ci`，按现有游戏包公开接口开发，不复制别人的整个工作目录和未提交修改。

## 人工接手

```powershell
npm run game:task -- hold 123
# 等待原 GPT 任务停止写入，再在它的工作目录修改
npm run game:task -- ready 123
```

`automation:hold` 优先于 ready，会阻止控制器同步分支和合并。所有 GPT 写入者必须遵守 AGENTS.md，写入、推送前检查标签；该标签不能阻止已经在运行且不遵守约定的外部编辑器。一个分支同一时间只有一个写入者。尚未建立 PR 的任务先停止对应 GPT 会话再接手。

## 游戏包和验收接口

每个游戏拥有代码、资源、规则、测试和 README。README 包含玩法、桌面及触屏操作、计分方式、设计要求和人工决定，后续 GPT 调整以其为准。稳定的游戏 ID、存储标识、历史关卡和每日挑战映射不得替换。

新增游戏只依赖现有 SDK。注册表允许追加新游戏的 manifest、rules、art 和动态加载器，以及对应工作区依赖、锁文件链接；自动策略会比较语法树和锁文件，拒绝在共享文件中夹带旧逻辑调整。目录、包名、manifest.id 必须一致，已有计分规则和关卡内容的修改转人工确认兼容性。公共日历、SDK、运行器、第三方依赖和计分版本调整另开人工确认的 platform PR。新增游戏先提供普通模式，纳入每日挑战日历属于独立的平台变更。

每个新增游戏提供 `games/<id>/qa/playthrough.mjs`：

```js
export async function play({ page, mobile, point, seed }) {
  // 页面已进入目标游戏、点击开始，并暂停浏览器时钟；真实后端种子为 seed。
  // point(x,y) 把逻辑画布坐标转换成当前桌面点击或触屏点击。
  // 在这里执行该玩法所需的真实输入；需要推进时钟时用 page.clock.runFor(ms)。
  // 返回前应真正完成一局并获得可参与排行榜的结果。
}
```

验收器负责检查结算、排行榜回执和刷新后存档；不得通过直接调用结算、改状态、绕过前端提交来满足检查。旧游戏首次修改时补齐场景；四款已有的 windmill/courier/weave/jugs 使用现有实玩脚本。

```powershell
npm test
npm run check
npm run api:build
# 浏览器运行器安装到已忽略目录，不修改项目依赖
npm install --prefix output/automation/browser --no-save --ignore-scripts playwright@1.62.1
$env:NODE_PATH = Join-Path (Get-Location) 'output/automation/browser/node_modules'
$env:PLAYWRIGHT_CHROMIUM_EXECUTABLE = 'C:\Program Files\Google\Chrome\Application\chrome.exe'
npm run verify:games
```

CI 会检查全部游戏的开始、暂停、重开和布局；对改动游戏执行桌面与触屏完整游玩，运行离线回归，并把真实前端请求送到生产处理器加内存 SQLite。测试服务器使用确定种子及加速时钟，不连接生产数据库；接口的时序、防刷、幂等、离线降级和校验错误由现有自动测试同时覆盖。首次搭建流程使用四款已有游戏进行真实结算，并通过扫雷验证真实榜单、幂等重试及刷新后的排名。现有八款原本机游戏已开放普通榜，须验证各自真实上榜链路；每日榜开放状态与日历保持不变。未来新增游戏同样须验证自己的真实上榜链路。报告和截图只保存在检查附件中。触屏模拟不等于实体手机验收。

## PR 与自动合并

推送任务分支，创建一个 PR，完成检查后标记 `automation:ready`。主分支保护要求 `game-verification` 检查通过、包含最新 main、线性历史，且管理员也不能直接推送、强推或删除主分支。个人维护的审批人数为 0。

控制器只运行 main 上的可信代码，重新判断文件范围、检查记录和当前提交；不运行 PR 的脚本。落后于 main 的游戏分支会先 rebase，并用精确的旧提交保护远端推送，再触发完整检查。冲突时添加 hold，不覆盖修改。每次只合并一个 PR，等发布完成再处理下一个。

PR 最终合入 main 统一使用 **Squash and merge**，每个 PR 只产生一条提交。开发分支可以保留多次调试和修复提交；上面的 rebase 仅用于同步最新 main，不是最终的 PR 合并方式。自动合并使用最新 PR 标题加 `(#PR编号)` 作为提交标题，正文留空，不拼接分支上的提交日志；人工合并也应检查并清理最终提交说明。合并前把 PR 标题整理为清晰的功能或修复概述，背景、验证与风险留在 PR 说明中。

机器人使用 GITHUB_TOKEN 时，推送和合并不会自然触发后续 push 工作流，所以控制器会显式 dispatch 新一轮验收和精确提交的发布。无需存储个人 GitHub 令牌，不使用原生无范围限制的自动合并开关。初始化配置命令默认只预览：

```powershell
npm run repo:configure
npm run repo:configure -- --apply
```

`--apply` 修改远端分支保护、合并方式和标签。应在新检查已成功运行后执行，避免锁住尚无必需检查的主分支。

配置预览应显示 `merge: "squash"`。应用配置时只允许 squash，关闭 merge commit 和 rebase merge，并将 squash 默认标题设为 PR 标题、正文设为空白，避免恢复旧的 rebase-only 设置。调整合并策略不改变必需 CI、准确头 SHA、最新 main、hold、游戏文件范围和人工确认要求；平台 PR 仍需人工确认。

## 发布、回滚与恢复

仓库 Secret `CLOUDFLARE_API_TOKEN` 需要具有当前账户 Worker 发布及现有 D1 绑定所需权限。令牌由仓库 Actions Secret 管理，不进入代码、PR 文本或日志；可在 GitHub 仓库 Settings → Secrets and variables → Actions 中配置。本流程不自动迁移数据库。

发布先构建并测试、保存网页产物，再部署后端、读取每款游戏的实际榜单、部署网页产物，最后核对线上版本及游戏模块。线上冒烟只读，完整结算使用 CI 的隔离环境。成功后保存 `release/<提交编号>` 和 `release/last-good`。

失败时建立 `release/hold`，阻止后续自动合并和发布。若网页部署已尝试，使用上一成功版本的 `release-site` 附件恢复网页；保留向后兼容的新后端，避免已打开的新游戏页面失去规则支持。平台变更若破坏后端兼容性，必须人工确认并恢复配套后端。回滚附件保留 30 天；首个新流程发布会尝试复用旧流程仍有效的 Pages 附件，没有可用副本则在部署前停止，先建立基线备份。

修复后运行：

```powershell
npm run release:resume
```

该操作明确解除暂停，并重新发布当前 main。不能在未查明失败原因时自动恢复。代码修复或回退都通过新 PR，不改写 main 历史。

## 游戏模式契约

合法配置有两种：只有普通模式，或普通模式加闯关模式。普通模式始终提供引擎、manifest、rules 和 art；只有闯关游戏才声明 manifest.campaign、包的 ./campaign 导出和注册表的 campaignLoader，并提供真实关卡数据。普通模式游戏不需要 campaign.js，也不应添加空关卡文件来通过验收。首页自动链接普通模式；其 /levels 路由返回未开放提示。每日挑战池保持历史映射，不因新增普通游戏而自动变化。

公共关卡测试按 manifest.campaign 选择游戏，验证所有声明的关卡；原有 28 款、560 关及原始内容哈希仍受保护。tests/game-modes.test.mjs 使用隔离的普通模式样例验证缺少 campaign 文件的合法配置，并检查双模式入口和路由。

## 排行榜接入、验证和恢复

每款游戏在 `manifest.leaderboard` 声明 `normal`、`daily` 和未开放时的 `reason`。前端、服务端开局校验与完整游玩验收读取同一配置。当前 30 款游戏均已开放普通排行榜；萤灯巡夜、风帆过峡、果篮天平、茶点跳跳棋、风车采蜜、花径送信、花窗数织和量水茶坊的每日榜仍关闭。每日挑战日历及既有映射不变，历史榜单仍可读取，固定关卡仍只保存本机进度。未来日历包含某款游戏不代表自动开放上榜，开放时需更新该游戏配置并验收，不改变历史日历。

灯塔方阵的普通/每日对局会记录翻灯和撤销操作。后端使用本局种子重放，核对步数、通关状态和首次通关后停止操作；缺少记录、错误棋盘、伪造零步通关或篡改记录均拒绝。计分方式、规则版本、历史存档和榜单数据不变。灯塔的结果请求上限为 128 KiB，记录最多 100000 个操作；其他请求仍限制为 8 KiB。其他游戏暂时保留原有范围与关联校验，此改动不代表所有游戏都已支持重放防作弊。可重放也不能区分人工操作与自动求解。

兼容性：已打开的旧灯塔页面不包含操作记录，部署新后端后需要刷新并重新开局才能上榜，已有本机成绩和关卡进度仍可读取。旧版已经接受的回执保持幂等，既有榜单中的可疑成绩不自动删除；处理历史成绩须另行确认范围。上线须通过人工确认的平台 PR，并先部署后端再部署网页。

已取得在线对局的成绩会在发送前写入独立本机待提交条目。临时错误按退避与 `Retry-After` 自动重试，恢复联网、刷新页面后继续使用原对局和原成绩；永久错误或到期后停止补交，并显示具体原因。离线开局不会补造在线对局。匿名身份仍由 HttpOnly Cookie 管理，不保存会话令牌到队列。浏览器存储不可用时只支持当前页面内重试，并显示原有存储不可用提示。

提交成功后，同游戏、模式和日期的已展开榜单自动刷新，并保留当前筛选。公开读榜直接 GET，不强制创建匿名身份；需要开局和个人资料时缓存已确认的匿名身份，服务端返回 401 时失效缓存。

## 总榜、每日榜与逐关榜

普通与每日成绩在读取总榜时合并，每位玩家按同一游戏规则保留最佳；历史记录立即参与，无需回填或迁移。每日挑战仍按原日期和游戏单独排名，日历、种子和计分版本不变。固定关卡不进入总榜。

排行榜 API 的 GET /v1/leaderboards 新增 mode=total；mode=normal 保持旧普通榜语义，mode=daily 保持原每日榜语义。mode=campaign 必须同时提供 level 和 campaignVersion；POST /v1/runs 同样接受这些关卡参数。逐关记录使用现有 normal 分区内的保留 challenge_date 命名空间 level:<版本>:<编号>，只允许由后端关卡参数生成，普通请求不能指定日期，因此无需修改 D1 结构或执行迁移。关卡版号以当前 manifest 为准，不跨版本混排。

逐关榜沿用本机策略：steps 按步数、用时排序，elapsed 按用时排序，action 按失误更少、得分更高、用时更短排序。记录字段 rounds 在保留关卡分区内保存 mistakes，响应转换回 mistakes。浏览器自动记录固定 1/60 秒更新与输入，服务端加载权威关卡并重放；最多 30 分钟、6000 次操作、512 KiB，超过范围仍可本机游玩但不能上榜。重放数据不永久写入成绩表。旧随心与每日提交接口及幂等回执继续兼容，总榜回执另含 totalRank。

客户端单次请求超时为 8 秒，榜单读取对网络错误、超时、408、429 和 5xx 最多重试两次，退避 0.5 / 1 秒并尊重 Retry-After。超过 5 秒的服务端等待要求交由用户稍后重试；写操作不做盲目重发，成绩提交继续使用持久队列及原始对局幂等键。手动提交重试可跳过本地退避，但不跳过服务端 Retry-After。展开的可见榜单每 30 秒刷新，网络恢复、回到页面、匹配的成绩接受后刷新；切换筛选或离开页面取消旧请求。只读看榜及昵称资料查询不创建匿名身份。

## 游戏入口资源恢复

普通和每日游戏页先挂载公共排行榜，再异步加载游戏引擎，网络故障不能隐藏看榜入口。普通、选关、关卡入口共用资源加载器：首次失败后按 0.5 / 1 秒退避最多重试两次，整个加载过程最多等待 12 秒。失败或超时显示具体原因及「重试加载」「刷新页面」；重试加载只重新进入当前路由，不清除本机记录。离开页面取消等待和退避，迟到的导入结果不能覆盖新页面；浏览器底层 import 不能被物理中断，因此保留用户手动刷新入口以应对模块求值失败等浏览器缓存状态。

scripts/module-recovery-qa.mjs 在临时数据库中覆盖桌面与模拟触屏的首次连接中断、持续失败、挂起超时、迟到响应、选关/关卡恢复，并使用真实输入完成恢复后的星轨邮差对局，检查结算、提交及榜单刷新。失败时保留 JS 资源路径、状态或网络错误、页面截图和运行时错误，不记录 Cookie 或请求头。完整 npm run verify:games 包含这些场景。

线上使用 RELEASE_SHA=<完整已发布提交> node scripts/entry-production-qa.mjs（浏览器依赖同常规验收器）执行只读复核：原跨游戏导航顺序、总榜/逐关/每日入口、2 次桌面及 5 次模拟触屏独立上下文中的星轨冷启动。所有 API 写请求均在发送前拦截，失败时保存同样的资源诊断，不能仅凭找不到排行榜按钮就归因于排行榜服务。
